# 상세 개발 기록

작업일: 2026-11-06. 아래는 실제로 수행한 순서와 결정이다. 분 단위 시간은 별도 측정하지 않았다.

## 01 — 입력 확인

- 사용자 제공 경로 `[로컬 프로젝트 폴더]`를 읽었다.
- 5개 파일과 README, index.html, app.js의 주요 흐름을 확인했다.
- 첨부 텍스트 전문을 읽었다. 파일명: 붙여넣은 텍스트.txt. 검토 대상 원본 ZIP은 받지 않았다.
- 문서의 ‘기존 FANPLAY’와 실제 폴더의 ‘Diamond Memories’가 다름을 확인하고 사용자에게 설명했다.
- 사용자가 ‘방향성과 작업을 전부 세세하게 기록’하도록 추가 요청했다.

## 02 — 방향 선택

- 첨부 문서의 현행화 권고대로 선수의 8시즌 커리어를 목표로 삼았다.
- 기존 파일을 바로 덮어쓰지 않고 현재 허용 작업공간의 fanplay-build에서 구현했다.
- Sites 스킬 중 로컬 제작 경로를 참고했고 외부 등록·배포는 수행하지 않았다.
- 라이브러리 설치 없이 HTML/CSS/JavaScript로 만들었다. 단순 실행과 수업 시연에 맞춘 선택이다.
- 새로운 브랜드 FANPLAY, 크림/그린 색조, 종이 티켓·다이아몬드 모티프를 결정했다. 이미지 검색·생성 도구는 사용하지 않았다.

## 03 — 데이터와 저장

- schemaVersion 2, tickets/posts/career/profile/inventory를 정의했다.
- 복원 과정에서 잘못된 티켓만 제외하고 잘못된 career는 null로 복구했다.
- 닉네임·팀·대표 참조·칭호·아이템·점수·사진 형식을 검증했다.
- 기존 fanplay-prototype-v1 키는 유지했다. 이 키가 없으면 diamond-v1을 읽었다.
- night/gold/trophy를 신규 steady/star/legend 아이템으로 대응했다. 과거 자유 문자열 칭호는 추측 변환하지 않았다.
- transact에 사본 우선 저장 구조를 넣고 저장 성공 후에만 FP.data를 교체했다.
- 완료 커리어와 보상을 같은 트랜잭션으로 묶어 시즌·보상 불일치를 막았다.

## 04 — 콘텐츠와 게임

- 8개 시즌 상황과 시즌별 선택 3개를 새로 작성했다.
- 투수에게는 등판·구위·제구, 야수에게는 타석·타격·수비 문구를 사용했다.
- 포수·내야수·외야수는 야수 시작값을 공유한다.
- 선택 능력치 증감과 직전 결과, 시즌 로그를 표시했다.
- 6번째 시즌에 현재 첫 능력치 60 이상 여부에 따른 보충 문구를 추가했다. 전면적인 분기 스토리는 아니다.
- 3개 결말과 공통 별, 결말 아이템·칭호 지급을 연결했다.
- 초기 최고 선택 증가 [5,4,5]에서는 레전드 경로가 1/6561뿐임을 자동 계산으로 확인했다.
- 최고 선택을 [6,5,6]으로 수정했다. 최종 분포는 꾸준함 1711 / 간판 4693 / 레전드 157이다. 투수와 야수의 시작 합계가 같아서 분포도 같다.
- 경로 수는 사용자 획득 확률이 아니다. 선택 분포를 조사하지 않았으며 재미·밸런스 검증이라고 주장하지 않는다.

## 05 — 티켓과 수집함

- 3단계 폼, 경기 기록, 직관/중계, 점수, 장소, 태그, 감상을 구현했다.
- 클래식/전광판/포토, 4색, 실시간 미리보기를 연결했다.
- JPEG/PNG/WebP, 12MB 제한, 900px 축소, JPEG .68 변환을 구현했다.
- 비동기 사진 처리 중 다음 단계 이동을 막고 사진 제거를 제공했다.
- 잠금 보상은 획득 조건과 비활성 입력으로 표시하고 저장 함수에서도 재검사했다.
- 티켓 ID 기준 업데이트로 수정 시 복제 생성을 막았다.
- 수집함 필터, 상세/수정, 대표 지정, 삭제, 게시를 추가했다.
- 대표 티켓 삭제 시 참조를 null로 정리하고 게시글의 티켓 사본은 유지했다.

## 06 — 프로필과 커뮤니티

- 닉네임, 10개 구단 강조색, 대표 티켓, 선택 칭호, 보상 목록과 조건을 표시했다.
- 보유 티켓·게시·아이템 수, 최근 저장 티켓과 현재 커리어를 표시했다.
- 게시할 때 티켓 사본을 저장하고 좋아요 0/1 토글, 댓글 등록, 게시글 삭제를 구현했다.
- ‘로컬 시연’이라는 안내를 커뮤니티 화면과 README에 넣었다.
- 사용자가 보낸 실제 게시물이나 메시지는 없으며 외부 서비스로 전송하지 않았다.

## 08 — 검사와 관찰된 문제

- node --check로 JavaScript 구문을 검사했다.
- 초기 작성 중 반응형 CSS의 repeat(2,1fr)) 오타를 찾아 닫는 괄호 하나를 제거했다.
- integration 11개 검사를 실행했다. 모든 검사 통과, 13,122개 경로 계산 포함.
- screens 12개 렌더 검사 통과. 최소 DOM 대체 환경으로 실행했으며 실제 브라우저 클릭 시험은 아니다.
- Python 정적 서버를 8765 포트로 실행하려 했고 IAB로 localhost:8765를 열었지만 연결 시간 초과였다.
- PowerShell HTTP 확인도 소켓 접근 권한 제한으로 실패했다. 실제 페이지 200 응답이나 브라우저 렌더 성공을 확인했다고 기록하지 않는다.
- 실제 사진 처리·모바일 외관·키보드 전 흐름은 사용자의 브라우저 검수가 필요하다.

## 09 — 반영 정책

지정 폴더에 반영하기 전에 현재 5개 파일을 archive의 고유 백업 폴더에 복사한다. 파일을 이동·삭제하지 않는다. 11.03_test.html은 원래 경로에도 그대로 남긴다. 새 index는 css/style.css와 js/*.js를 사용하므로 기존 루트 app.js/style.css는 남지만 새 진입점에서 로드하지 않는다. 설치 manifest는 백업 경로와 배포 파일 목록·해시를 기록한다. sources는 건드리지 않는다.

## 후속 권장 작업

실제 PC/휴대전화에서 시연 순서를 수행하고 결과를 검사표에 추가한다. 실제 과제 안내문과 게임 유형을 대조한다. 사용자 5~10명의 관찰을 기록한 뒤 문구와 밸런스를 조정한다. 원본 ZIP이 제공되면 기존 FANPLAY 필드 변환을 실제 샘플로 검사한다. GitHub Pages 배포가 필요하면 별도 요청에 따라 준비한다.

## 10 — 모바일 브라우저 후속 개선

사용자가 휴대전화 브라우저를 주요 환경으로 확정하여 하단 6메뉴, 터치 영역 확대, 16px 입력, 안전 여백, 폼 우선 순서, 좁은 티켓 배치를 적용했다. 상세 결정과 미검증 항목은 mobile-update.md에 기록했다. 후속 수정 전 상태도 archive에 백업한다.
