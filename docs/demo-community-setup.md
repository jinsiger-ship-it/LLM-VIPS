# FANPLAY v0.9.0 시연용 아이디와 커뮤니티

회원가입에서 시연용 아이디와 응원팀을 선택한다. 로그인에서 가입한 아이디의 테마와 기록을 불러온다. 같은 아이디를 아는 누구나 게임과 티켓 기록을 열고 수정할 수 있으므로 실제 개인정보를 넣지 않는다.

공개 글과 댓글의 소유권은 아이디와 브라우저별 비밀값으로 검증한다. 비밀값은 작성한 브라우저에만 저장되고 서버에는 해시를 보관한다. 목록이나 게임 기록에는 둘 다 포함되지 않는다. 같은 아이디를 다른 브라우저에 입력해도 기존 글을 수정하거나 삭제할 수 없다. 브라우저의 사이트 데이터를 지우면 그곳에서 작성한 공개 글과 댓글을 관리할 수 없으므로, 필요한 경우 운영자에게 문의한다.

공개 피드는 티켓·닉네임·게시 시각·좋아요·댓글을 보여 준다. 게시 버튼을 누르면 해당 티켓의 사진과 메모도 공개할지 확인한다. 게시 데이터는 최대 1MB다. 공개 게시글의 반응은 별도 테이블에서 집계하며, 좋아요는 브라우저와 아이디 조합당 한 번씩 누를 수 있다. 다른 아이디의 게시물은 개인 저장 데이터에 섞이지 않는다.

## 적용 순서

1. 기존 Supabase 프로젝트의 SQL Editor에서 [2026112402_demo_community.sql](../supabase/migrations/2026112402_demo_community.sql) 전체를 실행한다. 기존 `2026111801_demo_records.sql`이 적용된 프로젝트를 대상으로 한다. 이전 초안의 회원용 SQL과 Auth 설정은 필요하지 않다.
2. SQL Editor에서 `select public.fanplay_demo_ticket_feed('latest', 0);`을 실행한다. 게시물이 없는 경우 빈 배열이 정상이다.
3. 이전 개인 기록 중 공개에 동의한 글이 있다면 [선택 이전 SQL](../supabase/admin/20261124_publish_reviewed_legacy_posts.sql)의 조회문으로 확인한 뒤 선택한 글만 옮긴다. 작성 시각이 없는 글은 최신순 뒤에 표시된다. 기존 글의 사진·티켓 메모와 개인 반응은 옮기지 않는다.
4. 배포 후 다른 두 브라우저에서 같은 아이디의 게임 기록을 확인하고, 게시물의 수정·삭제 버튼이 작성한 브라우저에만 표시되는지 확인한다.
5. [로그인 조회 SQL](../supabase/migrations/2026112403_demo_login_lookup.sql)을 적용한다.
6. [회원가입 SQL](../supabase/migrations/2026112701_demo_signup.sql)을 적용하고 v0.10.3을 배포한다. 기존 기록은 유지되며 회원가입 호출만 새 아이디를 만든다.

기존 `fanplay_private.demo_records`, RLS, 관리자용 `fanplay_community_feed` 권한은 유지한다. 공개 앱은 반환 필드를 제한한 `fanplay_demo_ticket_feed`를 사용한다. 최신순 목록은 한 페이지에 20개, 좋아요순과 댓글순은 각각 상위 10개를 표시한다. Realtime 알림을 받으면 목록을 갱신하며, 연결 상태와 별도로 화면을 열어 둔 동안 12초마다 확인한다.

## 로컬 검증

- `node tests/demo-community.cjs`는 `PGLITE_MODULE`로 지정한 로컬 PostgreSQL에서 두 아이디의 공유 피드, 동일 아이디의 브라우저별 쓰기 권한, 좋아요·댓글, 기존 기록 보존, 선택 이전을 확인한다.
- `node tests/browser-demo-community.cjs`는 `PLAYWRIGHT_MODULE`과 `BROWSER_EXECUTABLE`로 지정한 브라우저에서 320·390·768px 화면과 복수 브라우저 흐름을 점검한다. 외부 DB 요청은 로컬 응답으로 대체한다.
